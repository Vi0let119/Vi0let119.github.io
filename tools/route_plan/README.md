# 扫街路线规划器（Street Shoot Planner）

面向**旅游扫街摄影**的单日路线规划工具：在地图上选点 → 受时间窗约束的最优顺序（TSP-TW）→ 全程到达/离开时刻表 → 地图上可视化路线 → 一键导出文字计划。

纯前端（React + Vite + TypeScript），无后端；地图与路线数据来自高德 JS API 2.0。

## 核心能力

- **地图选点**：POI 关键词搜索 / 点击地图加点 / 拖拽图钉改坐标 / 起点可单独设置 / **拖拽松手后自动重算路线与时刻表**
- **两种生成方式**
  - ⚡ 自动规划：Held-Karp 精确 DP（≤16 点）求解受时间窗约束的最优访问顺序；大规模自动退化为「最近邻 + Or-opt/2-opt」启发式
  - 手动排序：拖拽调整顺序，同一时刻表引擎即时计算
- **时间规划（到达/离开时间戳）**：起点出发 → 全程时刻表（含起点 → 第 1 站路段）；早到自动等待；硬窗晚到标红冲突并给出建议；软窗晚到计入罚分
- **摄影化的时间窗**：绝对时间窗 + **日落相对窗**（如「日落 ±30 分钟」），点位卡片直接显示当天日出/日落/蓝调时刻
- **五种交通方式**：
  - **智能混合（默认）**：逐段自动选择——步行距离 <2km 或步行时间 ≤ 公交时间 → 步行；否则公交地铁；公交无方案自动退回步行
  - 步行 / 公交地铁（含换乘分段）/ 骑行 / 驾车
- **地图可视化**：序号标记 + 到达时间气泡 + 真实道路路线 + 段中点「方式 距离·耗时」标签；**每条路线唯一配色**（20 色精选盘，≤17 段不重复，时间轴同色圆点对照）；**线型只由方式决定——步行虚线、乘车/骑行/驾车实线**（估算不改线型，只标注「（估算）」并降低不透明度）；公交车辆段永远压在步行虚线之上，重叠不遮挡；冲突点红色脉动；失败路段降级为直线并标注「估算」
- **详细换乘明细**：公交/地铁段在时间轴与导出中展开分步行——每段独立呈现「方式/线路 · 站数 · 距离 · 时长 → 目的地」（如 `🚇 地铁15号线 · 3站 · 4.3km · 14m → 上海西站`），路段行给出**步行与乘车的拆分合计**（如 `步行 1.9km · 36m ｜ 乘车 12.3km · 31m`）
- **时间轴 ↔ 地图联动**：点击时刻表里的**路段**（含每条换乘子步骤）→ 地图自动缩放聚焦该段路线并高亮（该段加粗提亮、其余段变暗），时间轴对应行同步高亮；再次点击或点击地图空白处取消。点击站点条目则定位到对应点位。
- **导出**：完整版 Markdown（时刻表 + 交通详情 + 备注）/ 纯文本 TXT（逐段 ↳ 明细，可复制到剪贴板）/ JSON 存档（可回导）

## 快速开始

环境要求：Node.js ≥ 18。

```bash
npm install
npm run dev        # 打开 http://localhost:5173
```

首次打开会显示 **Key 配置引导页**，按以下步骤申请高德 Key（免费，约 5 分钟）：

1. 打开 [高德开放平台控制台](https://console.amap.com/dev/key/app) → 应用管理 → 我的应用 → **创建新应用**
2. 在该应用下 **添加 Key**，服务平台选择 **Web端(JS API)**
3. 复制生成的 **Key** 与 **安全密钥(jscode)** 两个值，粘贴进引导页（或写入 `.env.local`）

配置方式二选一（`.env.local` 方式见 `.env.example`，该文件不进版本控制）：

```
VITE_AMAP_KEY=你的Key
VITE_AMAP_SECURITY_JS_CODE=你的安全密钥
```

> 本地 localhost 使用可留空白名单；部署到静态托管时按域名配置白名单即可。
> 注意：浏览器不能直连高德 Web 服务 REST 接口（CORS 限制），本项目所有地图数据都经由 JS API 插件获取，属官方推荐通道。

npm run build      # 类型检查 + 生产构建 → dist/（站点入口：tools/route_plan/dist/index.html）

## 使用流程

1. **加点**：左上搜索框搜地点（回车），或「+ 地图选点」后点击地图任意位置（Esc 取消）
2. **设起点**：默认起点为华东师范大学普陀校区（历史存档中仍是旧默认人民广场的会自动迁移）；起点卡片可搜索/地图点选修改
3. **设约束**：点位卡片「编辑」→ 停留时长、打卡窗口（无限制 / 绝对时间窗 / 日落相对窗）、硬窗或软窗、备注
4. **生成**：顶部「⚡ 自动规划」求最优顺序；或拖拽卡片排序后点「按当前顺序生成」
5. **查看**：地图上标记显示到达时间，时间轴与地图联动（点条目定位）；冲突点红色标出
6. **调整**：直接拖动地图上的图钉修改位置，松手约 0.7 秒后自动重新规划（沿用上次的规划方式）
7. **导出**：右上「导出 ▾」→ Markdown / TXT / 复制 / JSON 存档

## 技术要点

### 求解器（`src/solver/`）

- `tspTw.ts`：**精确 DP**。状态 `dp[mask][i]` = 已访问集合 mask、最后停在 i 的「最早完成时刻」。支配性依据：早到允许等待 ⇒ 更早到达永不吃亏（后续可行域与增量均为单调），故单值即最优。存在软窗时升级为 **(完成时刻, 罚分) 双指标 Pareto 前沿**，保证软窗语义下仍精确。
- `heuristics.ts`：最近邻（硬窗/紧迫度感知）+ Or-opt/2-opt 局部搜索；DP 判定无解时切换「最少违规」模式输出建议方案。
- `schedule.ts`：**时刻表引擎 —— 到达/离开时间戳的唯一事实源**。手动与自动两条路径共用，保证结果结构、地图渲染、导出完全一致。
- `amapTravel.ts`：距离矩阵服务（4 并发、超时重试、**localStorage LRU 缓存**、失败降级为「直线 × 绕行系数」估算）。改窗口/改目标/重排序重算时命中缓存，**零高德配额消耗**。

### 约束框架（`src/constraints/`）—— 为天气/光照等预留

所有影响「某点到达时刻是否可行 / 代价多少」的规则都实现 `SchedConstraint` 接口（resolve 解析相对窗口 → evaluate 评估到达时刻）。求解器与时刻表只消费解析后的绝对窗口，**新增约束不改 DP 一行代码**。

- v1 已实现：`time-window`（绝对 + 日落相对）、`sunTimes`（日出/日落/蓝调/黄金时段，SunCalc 本地计算）
- 预留槽位：`opening-hours`（高德 POI 营业时间）、`weather`（Open-Meteo 预报 → 软惩罚/建议改期）、`priority`（必拍/可选，无解时自动舍弃可选点）

### 智能混合模式（`src/services/mixedRule.ts`）

两点间的出行方式逐段决定：**步行距离 < 2km 或步行时间 ≤ 公交时间 → 步行；否则公交地铁；公交无方案 → 退回真实步行值**。矩阵构建分两阶段——先拉步行矩阵（<2km 的路对不再查公交，省配额），仅对 ≥2km 的路对查询公交时间做比较；结果记录在 `Matrix.legModes`，时刻表/渲染/导出逐段使用。

### 公交/地铁的时间依赖（`src/services/planRunner.ts`）

公交耗时随出发时刻变化 ⇒ 两阶段：求解用**参考出发时刻**的矩阵（按 15 分钟桶缓存）；排完序后按**每段实际出发时刻**复核一轮（仅复核被选为公交的段），单段差异 > 2 分钟则顺延后续时间戳并二次检查硬窗。公交请求受 QPS 限制（约 3 次/秒），已按「串行 + 间隔」节流。

### 路线可视化规则（`src/map/legStyles.ts`）

- **线型只由方式决定**：步行（含公交段的接驳步行）一律虚线，公交/骑行/驾车一律实线；估算降级不改线型（标签「（估算）」+ 降低不透明度）；
- **每条路线唯一颜色**：20 色精选盘按段序号取色，相邻段色差最大，单日上限（16 点 + 返程 = 17 段）内绝不重复；时间轴圆点与地图线条同色对照；
- **平行偏移**：所有路线沿行进方向右侧偏移约 10 米（与导航软件惯例一致），**来回路线自动分居道路两侧**，重叠不可辨认的问题在源头解决；
- **分层**：公交车辆段 > 公交接驳步行 > 单模式路段，重叠时高亮线不被覆盖。

## 常见问题

- **地图空白 / Key 未生效**：确认 Key 类型是「Web端(JS API)」且已填安全密钥；修改后需刷新页面。
- **规划很慢**：首次规划需要 N² 次路径请求（16 点约 272 次），完成后进入本地缓存；之后改窗口/排序重算都是秒级。
- **部分路段标「估算」**：高德接口失败或超配额时的降级结果，会以黄色提示；稍后重试即可（估算结果不进缓存）。
- **数据与合规**：Key 只存本机；路线数据仅本地缓存自用，导出文件只含时刻表文本。换 Key 在「⚙」中重新配置。
