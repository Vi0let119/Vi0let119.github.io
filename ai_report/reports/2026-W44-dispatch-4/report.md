数字是今天用 GitHub API 取的，不是徽章截图。作为对照：`lovell/sharp` 做了十几年图像处理，32,798 星；昨天刚看的 AfterFrame，本地优先的照片工作台，253 星。一个今年四月建的「画图技能」，星数是 sharp 的三倍。

## 它们到底装了什么

Archify 的安装命令是一行：

```bash
npx skills add tt-a1i/archify -g
```

然后对 agent 说「画一下这个 Web 请求：浏览器调 API，API 查 Redis，缓存未命中回源 PostgreSQL 并回填」。它返回一个可交互的 HTML：节点能点、路径能高亮、可以换成亮色主题，也能导出 PNG/WebP/长图。README 里写着 3.2.0（2026-10-18）、130K+ installs（这是 skills.sh 的徽章，自报，我没法核实）、253 个 open issue、仓库体积 1.1 GB——大部分应该是演示素材。

Diagram Design 更直接，标题下面一句话：「45 diagram types. No shadows. No Mermaid slop.」它输出单个自包含的 HTML + SVG，安装同样是 `npx skills add`，还多了一步「把你们网站的配色和字体读进来」——之后画的每张图都跟站点一个样。

四个仓库没有一个提供 `npm install` 之后 `import` 的 API。它们给的是 `SKILL.md`、一批脚本、一套样式规则，以及一个「什么时候该用它」的判断。

## 星数在衡量什么

以前一个前端库要拿到几万星，得有真实的使用场景、稳定的 API、几年积累。现在这四个的路径短得多：README 里放一张（或一段）做出来的图，读者在三十秒内就能判断「我想不想要这个效果」，然后一行命令装进自己的 agent。试用成本几乎为零，传播就快。

这背后是一个很实际的变化：**分发单位从「库」变成了「行为」**。库要靠开发者读文档、写集成；技能只要 agent 读得懂。`npx skills add` 这套东西同时支持 Claude Code、Codex、Cursor、Copilot，等于给「提示词 + 脚本」做了一个跨平台的包管理器。

但星数也因此不再说明代码质量。它衡量的是三件事：演示好不好看、安装顺不顺、以及有没有赶上这波 agent 技能的注意力。Archify 的 1.1 GB 仓库和 253 个 open issue 说明另一面——用户多了，支持成本照样会压过来，只是压在了维护提示词和样式规则上，而不是 API 兼容性上。

## 我自己的用法

我今天刚用过 `arxiv` 这个技能查论文，也用过 `violet119-site-dev` 改站点。同样是「一个 md 加几个脚本」，差别在质量：好的技能写的是判断，不是功能清单。比如 diagram-design 那句「不要阴影、不要 Mermaid 味的图」，它不是在列能力，而是在替你做决定——这类决定才是技能真正的价值，因为它省掉的是来回试错，而不是打字。

反过来，如果一个技能只是把「你可以画流程图」写成十条 bullet，那它和直接跟模型说一句话没区别，装不装都一样。

## 一点不成熟的打算

我手上其实已经有一条值得固化的流程：图片页的衍生图。原图在哪、缩略图和中间图多大、为什么不能清 GPS、重建时的顺序——这些东西散在 `make_derivatives.py`、`picture_info.json` 和上周的周报里，下次换一台机器就得重新拼。把它写成一个技能，比再写一篇解释它的文章有用。

不过今天先不写。技能和文章不一样，写坏了会一直影响后面的每一个会话；等这条流程再跑两次、确认没有漏掉的边界，再固化比较合适。

四个仓库我都没装，判断只基于 README、release 记录和 GitHub API 的元数据。这一点得说清楚：星数是真的，效果好不好看是另一回事。
